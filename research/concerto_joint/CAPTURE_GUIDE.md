# 新音符样本：先把一条记录走通

先提供一段战斗的完整前后记录，再提供一次103或104兑换的前后记录，用来验证采集流程。两条记录不足以估计概率；确认流程能读全后再扩大数量，不预先宣称几条就能训练。

## 能录屏时

1. 记录区服、游戏版本、塔和楼层；展示本队主辅秘纹及其阶段，详情页能看见星数和等级时一起保留。
2. 战斗前把音符库存实际数量拍全。需要滚动或翻页的部分全部保留；没显示的种类仍是未知，不填0。
3. 完成这一场战斗，期间不混入买音符、NPC等奖励，再把同一库存的全部数量拍全。掉落动画不能代替库存读数。
4. 遇到五音符换150币或十音符换稀有潜能时，另录兑换前库存、完整菜单、实际选择、结果和兑换后库存；尽量保留自然出现的不均衡库存，便于区分随机扣除机制。

第一次先确认游戏界面是否能取得全部13种实际数量。如界面不能显示全，只记录能读到的部分，我们会标为不完整，不补成完整向量。

2026-11-10实录发现：对局中的9图标音符条会隐藏辅助秘纹带入的塔外音符。例如光地塔的条中不显示水，但背包放大镜详情与结算页明确显示水7。必须打开详情列表并滚动到底，不能把条中缺失的种类当成0。入塔首帧还可能处于奖励数值更新中；等动画结束，在稳定的选择界面或背包记录。多视图拼接只能发生在同局暂停、没有其他音符动作期间。

分别爬三座塔可以覆盖13类音符的读数，但三局的库存不是同一状态，不能拼成一条13维前后样本。新增实录与对账见 [TOWER_CAPTURE_20261110.md](TOWER_CAPTURE_20261110.md)。

## 能导出日志时

优先保留同一动作对应的原始请求／响应与前后库存。需要的不是另一份商店OCR汇总：

- 稳定的对局、动作标识与顺序；已发生操作的确认来源，不能只凭Maa回报成功。
- 90011..90023完整前后库存，明确读到的0保留0，未取得值为null。
- 原始 `Data.Infos` 全数组，以及其中 `Tid/Qty/New/LuckyLevel`；Qty必须保留正负号。原始值缺失时保持null，不编造空数组。
- 战斗的数量预览、胜负、奖励来源、队伍／秘纹ID与阶段／条件；兑换的选项、实际减少量和金币／潜能结果。
- 12002同时保留前后生命、最大生命和分支结果；114保留题目、完整菜单顺序、显示索引、失败禁用项和实际结果。
- 商店继续保留完整未购物货架、店序、初始／刷新与流水号；同一货架重读不算独立样本。

日志和视频先本地处理，不把玩家身份、令牌或完整原始包提交到公开PR。

## 模型侧接收格式

`data/capture_template.json` 是待填写模板，null明确表示未知；空模板不能作为训练样本。规范化记录按JSONL逐动作保存，原始证据另存并关联。转换不能把历史菜单／商品描述推断成库存。

```bash
python research/concerto_joint/capture_records.py /local/note_transitions.jsonl --output /local/capture_audit.json
```

检查区分零与缺失、操作确认与软件成功、未关联动作、显式训练／概率排除标记、前后库存与有符号增减不一致，以及同动作重读／冲突。通过只表示采集结构可用，后续仍需人工核对真实来源、分组独立性和概率校准；不会自动开始训练。
